## ADDED Requirements

### Requirement: Advanced solver execution is explicit

The system SHALL distinguish executed advanced solvers from readiness-only capability rows for the food supply-chain case.

#### Scenario: Solver comparison is requested

- GIVEN the food case Excel data is readable
- WHEN `/api/cases/food-supply/optimize/solver-compare` is called with advanced mode enabled
- THEN the response SHALL include rows for network design, dispatch, metaheuristic, Pareto, and optional runtime solvers
- AND each row SHALL include `solver_id`, `solver_family`, `execution_mode`, `provider_status`, `deployable`, `metrics`, and `fallback_reason`
- AND readiness-only rows SHALL NOT imply that the solver executed.

### Requirement: Network design can use bounded exact MILP

The system SHALL attempt bounded exact MILP network design for the food case when Gurobi or CPLEX/docplex is available and requested.

#### Scenario: Exact network design is requested

- GIVEN bounded facility and customer limits
- WHEN `/api/cases/food-supply/optimize/network-design` is called with `solver_mode=milp`
- THEN the response SHALL either execute an exact MILP and return `execution_mode=exact_milp`
- OR return a degraded/fallback response that names why MILP could not execute
- AND the response SHALL validate facility capacity/assignment constraints.

### Requirement: Dispatch can use bounded VRP and metaheuristics

The system SHALL support bounded dispatch optimization through OR-Tools VRP, pyVRP, and metaheuristic comparison while preserving capacity and unique assignment constraints.

#### Scenario: VRP dispatch is requested

- GIVEN a bounded B-end demand wave and case vehicle resources
- WHEN `/api/cases/food-supply/optimize/dispatch` is called with `solver_mode=ortools`
- THEN the response SHALL include route plans, assigned/unassigned counts, solver metadata, and constraint validation
- AND capacity violations and duplicate assignment violations SHALL be explicitly reported.

#### Scenario: pyVRP dispatch is requested

- GIVEN a bounded B-end demand wave and case vehicle resources
- WHEN `/api/cases/food-supply/optimize/dispatch` is called with `solver_mode=pyvrp`
- THEN the response SHALL either execute pyVRP and return `solver_family=pyvrp_cvrp`
- OR return a degraded/fallback response that names why pyVRP could not execute
- AND capacity violations and duplicate assignment violations SHALL be explicitly reported.

### Requirement: Pareto search can use pymoo NSGA

The system SHALL use pymoo NSGA for bounded food-case multi-objective comparison when available.

#### Scenario: NSGA Pareto is requested

- GIVEN bounded case inputs
- WHEN `/api/cases/food-supply/optimize/pareto` is called with `algorithm_family=nsga`
- THEN the response SHALL include a Pareto front with cost, carbon, freshness risk, and service level objectives
- AND report whether the front was generated by `pymoo_nsga` or deterministic fallback.

### Requirement: Road matrix provenance is transparent

The system SHALL expose real-road and local-baseline matrix provenance without mislabeling local distances as real navigation.

#### Scenario: Matrix build is requested

- GIVEN a requested `matrix_mode`
- WHEN `/api/cases/food-supply/distance-matrix/build` is called
- THEN every returned matrix row SHALL include `distance_source`, `path_source`, `authenticity_level`, and `fallback_reason`
- AND `haversine` or local PostGIS baselines SHALL NOT be labeled as provider navigation.

#### Scenario: Provider or OSM matrix is available

- GIVEN a small bounded matrix request and configured provider/OSM graph capability
- WHEN matrix mode is `amap`, `tianditu`, or `osm`
- THEN successful rows SHALL be labeled with the matching provider/network source
- AND failed rows SHALL fall back per pair with explicit `fallback_reason`.

### Requirement: OSM GraphML cache and route geometry preview are explicit

The system SHALL support food-case route geometry preview through local GraphML or provider polylines without mislabeling fallback geometry.

#### Scenario: GraphML cache status is requested

- GIVEN the food case module is available
- WHEN `/api/cases/food-supply/osm-cache/status` is called
- THEN the response SHALL include cache path, existence, cache kind, provider status, and fallback reason
- AND it SHALL NOT require provider keys or network access.

#### Scenario: Route preview is requested

- GIVEN a source node code, target node code, and route provider
- WHEN `/api/cases/food-supply/routes/preview` is called
- THEN the response SHALL include a WGS84 `polyline`, distance/duration, `distance_source`, `path_source`, `authenticity_level`, and `fallback_reason`
- AND provider or OSM failures SHALL return a visible fallback polyline rather than a 500.

#### Scenario: Food case GIS page displays route preview

- GIVEN route preview data has loaded in the Vue food case page
- WHEN the user opens the GIS network tab
- THEN the page SHALL display the route geometry, selected provider, source/target nodes, distance, and degradation metadata without relying on hover-only discovery.

### Requirement: Route provider comparison is visible

The system SHALL compare multiple food-case route providers for the same source/target pair without hiding degraded providers.

#### Scenario: Route provider comparison is requested

- GIVEN a source node code and target node code
- WHEN `/api/cases/food-supply/routes/compare` is called
- THEN the response SHALL include bounded rows for requested providers
- AND every row SHALL include provider status, distance/duration, `distance_source`, `path_source`, `authenticity_level`, and `fallback_reason`
- AND every row SHALL include `quality_score`, `quality_band`, and a `score_breakdown` for provider status, authenticity, geometry, fallback state, and relative distance
- AND the response SHALL include a recommended route selected from deployable provider/polyline quality, not from a hidden fallback.
- AND the response SHALL include summary metrics for provider count, geometry count, exact count, best distance, recommended provider, recommended score, best quality score, average quality score, and recommendation reason.

#### Scenario: Food case GIS page displays provider comparison

- GIVEN route comparison data has loaded in the Vue food case page
- WHEN the user selects a provider comparison row
- THEN the page SHALL update the displayed route geometry and keep comparison metadata visible without relying on hover-only discovery.
- AND the page SHALL display a compact metric strip explaining route count, recommended provider, route quality, degradation count, and recommendation rationale.
- AND the page SHALL display provider score cards so users can compare route quality without interpreting raw metadata fields manually.

### Requirement: Route comparison history is reproducible

The system SHALL persist food-case route comparison cache/history only in case-specific tables and SHALL never mutate production shipment, order, vehicle, or raw case fact tables when recording route comparison history.

#### Scenario: Route comparison is saved for replay

- GIVEN a source node, target node, and bounded provider list
- WHEN `/api/cases/food-supply/routes/compare` is called with `persist=true`
- THEN the response SHALL include `cache_status`, `cache_entry_id`, and `request_hash`
- AND the saved record SHALL include route summary, recommendation metrics, provider provenance, and diagnostics
- AND the saved record SHALL be stored in `case_food_route_comparisons`.

#### Scenario: Route comparison cache is reused

- GIVEN a non-expired cached route comparison with the same request hash
- WHEN `/api/cases/food-supply/routes/compare` is called with `use_cache=true`
- THEN the response SHALL return the cached comparison with `cache_status=hit`
- AND it SHALL keep the original `distance_source`, `path_source`, `authenticity_level`, and `fallback_reason`.

#### Scenario: Route comparison history is displayed

- GIVEN route comparison history exists
- WHEN `/api/cases/food-supply/routes/compare/history` is requested
- THEN the response SHALL return lightweight history rows with source/target, providers, recommended provider, recommended score, route count, geometry count, created time, and cache age
- AND the Vue GIS page SHALL display the latest history without requiring the user to inspect raw JSON.
